# REFRESH：HTTP 契约与运维限制

REFRESH 检查已有的代理缓存条目，并可能使其失效。它不会下载替换用的响应体，也不会延长条目的过期时间。内容已确知过期时请使用 PURGE；需要更新一个已过期的 GET 响应时，请使用 NGINX 原生的缓存再验证。

先阅读[配置示例](EXAMPLES.zh-CN.md#generation-and-refresh-example)。请保护管理端点，并保持其源站映射显式可控。

## 与 HTTP 标准的关系

`REFRESH` 是本模块自定义的方法，不在 [IANA 方法注册表](https://www.iana.org/assignments/http-methods/)中。它会改变缓存状态，必须按不安全的运维操作对待。在任何中间层或方法白名单中都要显式放行。该方法不定义请求体格式；选择条件应通过 URI 或 `cache_purge_key` 使用的请求头发送。

源站探测使用 HEAD 以及缓存的 `If-None-Match` / `If-Modified-Since` 校验器，二者由 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-13) 定义。条件由源站判断，ETag 优先于日期，弱 ETag 对这种检查同样有效。允许使用条件式 HEAD，尽管 [RFC 9110 §13.2.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.2.1) 指出它相对普通 HEAD 几乎没有响应体积收益；在这里，条件状态正是模块做保留/失效决定的依据。

这**不是** [RFC 9111 §4.3.4–4.3.5](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.3.4) 所述缓存再验证的完整实现。那套机制包含选择已存响应并更新元数据。v4 的探测在收到 `304` 时保持文件不变，但不会合并新的 `Cache-Control`、`Vary`、校验器或其它响应头；它也不会比较 `200` HEAD 的元数据来保留内容实际未变的对象。不要依赖 REFRESH 来应用新的缓存策略或延长新鲜度。若有这些需求，请使用原生的再验证，或显式 PURGE 后重新填充。

管理响应在页面处理完成时返回 `200`，包括含逐条错误或需要续页的页面；选择条件或游标非法返回 `400`，目录扫描失败返回 `500 scan_failed`。错误使用 [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html) 的问题格式，HTTP `status`、`type: about:blank` 与模块的 `code` 扩展彼此一致。完整约定见[响应契约](HTTP_RESPONSES.zh-CN.md)。

## 客户端必须处理的情形

| 情形 | 当前行为 | 运维后果 |
|---|---|---|
| 源站返回 `304` | `kept`；文件与 TTL 不变 | 内容按既有策略继续缓存 |
| 源站返回 `200` | `invalidated` | 校验器缺失或被忽略时同样如此；下一次 GET 会重新填充 |
| 源站返回 `404` 或 `410` | `invalidated` | 请确认探测配置命中的是同一份表示；因鉴权而被掩盖的 404 会导致不必要的清理 |
| 源站返回重定向、`401`、`403`、`412`、`429` 或 `5xx` | `upstream_status`；条目保留 | 不会跟随重定向；请查看原始状态并修复原因 |
| 源站未返回可用状态 | `transport_error`；条目保留 | 连接、TLS 或超时故障不能作为内容已变化的证据 |
| 条目带 Vary 元数据 | `skipped_vary`；不探测 | 已存文件无法重建原始表示所需的请求头 |
| 当前没有匹配文件 | `results` 为空 | 冷缓存或仍在填充的缓存不会被预热；空结果不能证明探测配置有效 |
| 探测配置不安全，或 URI 映射失败 | `skipped_profile`；不失效 | 配置错误会记录被拒绝的设置；映射失败可能只体现在结果中 |
| PURGE 与 HEAD 竞争 | 旧 generation 记为 `raced_replaced` | 过期的判断不会使后发生的 PURGE 所属 generation 失效 |
| 同一 generation 内文件被改写 | 可能采取保守的失效 | generation 保护不是针对文件的逐字节 compare-and-swap |
| 页面截止时间到达 | 停止发起新工作；`refresh_incomplete` | 已在进行的 HEAD 仍受核心代理超时约束；这不是硬性响应期限 |
| 客户端断开 | 停止分派；通过 NGINX 回调回收活动资源 | 先前的失效仍然有效；取消不是回滚 |
| 分配或 generation 失效失败 | `invalidation_error`；条目保留 | 检查共享内存压力和模块错误日志 |
| 仍有选中工作未分派 | 计入 `undispatched` | 续页不能跳过未完成的工作 |
| 存储扫描失败 | 返回 `500 scan_failed` 问题响应 | 查看错误日志；这种失败不会返回续页 JSON |

`complete: true` 表示本次选中的工作和页面都已处理完，而不是每个条目都被保留或成功失效。请逐条读取结果。对于 `complete: false` 的 `200` 响应，保持选择条件与探测配置不变，把 `next_cursor` 作为 `X-Cache-Purge-Cursor` 继续请求。尚未完成就超时的扫描会原样返回输入游标，并且不发起任何探测；一旦发现游标不再前进，应先解决时间或存储限制，而不是无限重试。

游标不是持久任务 ID、快照令牌或授权凭证。每页都会重新扫描目录，最多收集 32 个候选；并发文件变化会影响枚举结果。每个 worker 同时只有一个页面/探测，全局共享 16 个探测额度。相同的 REFRESH 调用不会去重；响应丢失后重试可能重复执行源站检查和失效，模块不承诺恰好执行一次，也不承诺结果集稳定。

## 配置前提

探测配置必须命中与缓存 GET 相同的主机、URI、查询串和表示。模块无法证明管理员写的静态映射是正确的，请只为已知的表示使用它，并使用显式的字面量请求头。不要依赖管理客户端的 Cookie、凭据、语言或 Range 头。校验会拒绝动态的表示头、转发请求头或请求体、缓存、错误拦截、非 HEAD 方法、公开可访问的 location，以及偏离所配置探测配置的内部重定向。

若源站使用 HTTPS，请为源站配置 NGINX 的上游证书校验、信任库和 SNI。REFRESH 不会引入独立的 TLS 策略。内部探测配置必须保持外部不可访问。

[覆盖说明](../../t/COVERAGE.md)区分了运行时检查、辅助函数层检查以及仍然存在的压力与平台缺口。这些限制属于公开契约的一部分；CI 通过并不会消除它们。
