# 模块组成

构建产物仍然是一个 NGINX 模块。其实现按职责拆分，源文件在 `config` 中显式列出。

| 文件 | 职责 |
|---|---|
| `ngx_cache_purge_module.c` | 模块注册、指令、配置与生命周期接线 |
| `ngx_cache_purge_handler.c` | HTTP 分派、访问检查、协议／缓存查找与精确清理 |
| `ngx_cache_purge_queue.c` | SHM 准入与去重、调度、worker 生命周期与状态指标 |
| `ngx_cache_purge_walk.c` | 有界目录遍历、原生缓存头校验、unlink 与 Vary 清理 |
| `ngx_cache_purge_invalidation.c` | 命名空间状态、generation 规则、缓存键绑定与失效 |
| `ngx_cache_purge_refresh.c` | 有界扫描、条件式 HEAD 子请求与续页 |
| `ngx_cache_purge_response.c` | HTTP 结果目录、响应头、转义与响应体 |
| `ngx_cache_purge.h` | 私有共享类型／契约与公共路径辅助函数 |
| `ngx_cache_purge_invalidation.h` | 私有失效接口 |
| `ngx_cache_purge_upstream.h` | 协议接口与版本相关的核心布局适配 |
| `ngx_cache_purge_posix.h`、`ngx_cache_purge_win32.h` | 平台文件系统操作 |

“Generation”指的是某个逻辑缓存键／命名空间的版本。提升该版本会让旧条目不可达，包括使用旧键的迟到写入。它只描述一种机制，并不覆盖 v4 的全部功能；该机制由失效组件负责。

私有头文件不构成第三方 ABI。拆分文件并不会消除对特定 NGINX 版本的缓存与协议结构的依赖；原生布局检查和边界构建用于覆盖这些依赖。

<a id="execution-ownership"></a>

## 执行所有权

worker 负责 HTTP 请求与完成回调。共享队列独立于提交请求，负责已接纳的物理清理任务。可选的核线程池执行文件系统操作；事件循环回调发布结果并释放准入额度。没有可用线程池时，增量执行使用有界遍历步进。REFRESH 只在事件循环中执行 HTTP 子请求。

NGINX 1.7.11 引入了线程池，但其 `epoll` 通知在安装回调之前就写出唤醒事件，worker 可能观察到空回调。该顺序在 NGINX 1.7.12 中修正。在受影响的早期 epoll 构建上，本模块会告警并对 purge/REFRESH I/O 使用增量执行。该回退不会修复旧核心线程池 API 的其他使用者。兼容性矩阵同时覆盖 1.7.11 的回退路径与 1.7.12 的线程池路径。

<a id="native-cache-loader"></a>

## 原生缓存加载器

当前设计在冷启动时不需要重建文件系统的标签索引。generation 规则与命名空间 epoch 无需在开始服务前发现每一个缓存文件。因此，复用原生缓存加载器并不会取代本实现中的任何启动引导流程。

若将来引入持久化的文件到标签索引，可以在原生加载器遍历期间填充它，从而避免第二次目录遍历。这需要定义元数据格式和一个核心集成点：`ngx_http_file_cache_loader` 是内部回调，而不是对外暴露的逐文件模块钩子。仅仅包装该路径的加载器回调无法暴露每个被访问的文件。任何集成都必须保留原生的 manager/loader 数据与生命周期，包括 1.11.5 中 manager 回调单位的变化。该边界的测试夹具只是原型，不是生产可用的加载器后端。

相关核心实现：[`src/http/ngx_http_file_cache.c`](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_file_cache.c)、[`src/event/modules/ngx_epoll_module.c`](https://github.com/nginx/nginx/blob/master/src/event/modules/ngx_epoll_module.c)，以及 [1.7.11](https://nginx.org/download/nginx-1.7.11.tar.gz) / [1.7.12](https://nginx.org/download/nginx-1.7.12.tar.gz) 源码归档。

<a id="execution-model"></a>

## 执行模型

一个**任务**是一次通配符或 `purge_all` 操作。一个**批次**是 worker 在限速暂停之前处理的任务数。一个**分片**是增量目录遍历中工作量有界的一步；一个任务可能需要许多分片。

启用 generation 键后，每个缓存路径与命名空间用一个物理扫描任务合并已接受的失效请求。REFRESH 页是独立 HTTP 操作，不属于 PURGE 队列任务。

| 请求和配置 | 文件遍历 | HTTP 完成时机 |
|---|---|---|
| 传统精确键，启用或未启用 Vary 匹配 | 请求 worker；Vary 增加一次目录遍历 | 操作结束后 |
| 通配符或 `purge_all`，后台队列关闭 | 请求 worker 同步遍历 | 遍历结束后 |
| 后台任务，使用所选线程池 | 每个 worker 同时最多一个线程池任务 | 接纳后返回 `202` |
| 后台任务，无可用线程池 | worker 事件循环增量分片 | 入队后返回 `202` |
| 队列容量或分配空间耗尽 | 请求等待接纳，不启动请求专属遍历 | 接纳后返回 `202` |
| generation PURGE，任意键形式 | 延迟扫描命名空间；请求内不打开或删除缓存文件 | 发布失效状态并入队后返回 `200 invalidated` |
| REFRESH 端点 | 有界扫描及最多 32 次串行 HEAD 探测 | 返回包含完成状态及续查字段的 `200` JSON |

未使用 generation 键的行描述传统行为。因容量等待的 generation 请求在获准后返回 `200`，不是 `202`。

一个增量分片最多执行 64 次目录迭代，或在观察到耗时达到 5 ms 时停止。跳过的条目与目录结束也计入预算。但该预算无法限制单次文件系统调用的耗时。

要将后台文件操作移到线程中，请使用 `--with-threads` 构建，并在 `http` 外部的 **main** 上下文定义核心线程池：

```nginx
thread_pool default threads=2;
```

`cache_purge_thread_pool <name>` 可在 `http`、`server` 或 `location` 中选择命名线程池，默认值为 `default`。引用 `default` 却没有显式声明时，NGINX 会以其标准参数创建该池。其他名称必须通过核心 `thread_pool` 声明。选择规则会继承；合并任务的执行池由第一个被接纳的请求决定。每个 worker 有自己的核心线程池。池满时保留任务的接纳配额，并在 10 ms 后重试投递，不会因此启动同步遍历。未编译线程支持、Windows、单进程模式，或 reload 后旧任务的池已被移除时，使用增量游标执行。

REFRESH 在所选线程池中为每个 worker 最多增加一个扫描任务。原生 HTTP 子请求在事件循环中运行，I/O 线程不访问它们的状态。

队列和索引的结构修改使用 slab 互斥锁。接纳与后台回调使用 trylock，忙时通过定时器重试。等待中**和运行中**的任务都保留在每个缓存路径的核心字符串 rbtree 中，通过完整键比较解决哈希冲突。该路径有 `Q` 个未完成任务时，索引操作为 `O(log Q)`；路径查找与已注册路径数量呈线性关系。等待与活动任务由原生 `ngx_queue_t` 链表管理。运行中操作的第一个重复请求安排一次重放，后续重复请求合并到该次重放。当前遍历结束后，重跑进入等待队列尾部，因此较晚的 PURGE 不会被默默丢弃。持续到来的新 PURGE 可能引发更多轮遍历。只有最终完成后才释放容量配额。文件操作与响应格式化在锁外执行。

rbtree 仅用于物理清理任务去重。generation 规则存储在独立 SHM 区域的有界字节 trie 中。命名空间扫描与传统键任务具有不同索引标识；REFRESH 的失效决定也进入同一清理流程。

队列已满或任务分配失败时，HTTP 请求通过 10 ms 重试定时器等待接纳，并使用核心的断连检测。请求及 cleanup 处理器保留在所属 worker，SHM 不保存请求指针。不会关闭 HTTP/2 或 HTTP/3 整条连接的读取。队列压力不会产生 429/503；已读入的短 PURGE 也不保证触发 TCP Zero Window。等待请求仍消耗内存与连接，请根据部署的连接预算使用核心超时和接纳策略。

已接纳任务在普通 reload 后保留键、池名称和临时路径保护设置。较新的重复请求会更新等待任务或下一次重跑的保护设置。禁止新的后台接纳不会丢弃已接纳工作。优雅退出的 worker 完成当前一轮后不再领取新任务。快速退出会将未完成的增量任务交回等待队列，不会在 exit hook 中完成整个文件遍历。已投递线程任务的生命周期由核心线程池销毁流程负责。

已分配任务由 PID 和槽位 epoch（slot epoch）标识：即使 PID 与槽位被复用，epoch 也能区分前后两任占用者。worker 每秒执行一轮恢复，最多检查 64 条活动记录，并将所有者已退出的任务重新入队。这可恢复失去所有者的任务分配，但不是事务日志。在共享链表或 slab 修改期间崩溃，仍可能破坏状态并需要重启。崩溃前刚执行的删除可能不进入指标。待处理任务和重跑需要存活的 worker；若要求完成，应在停止前排空。队列不持久化。

内部队列布局不是升级 ABI。更换为不同布局的构建时，需要完整重启；必要时先完成已接纳工作。同一构建的普通 reload 会复用共享区。

删除采用尽力而为语义。`202` 表示已接纳，不代表删除完成；遍历结束也不是缓存的原子快照。并发请求可能在遍历期间或之后创建缓存，文件错误会写入日志。通配符与全缓存遍历会 unlink 文件，但不会同步更新每个核心缓存节点。精确键和 Vary 操作会使匹配节点失效。

后台扫描失败后分别等待 100 ms、1 秒和 10 秒，最多重试三次。延迟任务保留去重记录和队列额度，但不阻止其他任务执行。新 PURGE 会重置重试窗口。耗尽次数后记录错误并移除任务；检查 `cleanup.exhausted`，修复存储问题后重试。物理清理失败不会撤销 generation 失效。文件已消失视为正常竞争，格式无效的文件会跳过，不会无限重试。
